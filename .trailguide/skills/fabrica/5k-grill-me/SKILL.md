# 5K Grill Me

Use Matt Pocock's `grill-with-docs` workflow through the bundled canvas: `grilling` plus `domain-modeling`. Read those skills when available; the rules below preserve their essential behavior when they are not installed. The UI changes presentation and answer transport, not who makes decisions or when implementation is authorized. When inherited grilling instructions describe frontier rounds or withholding blocked questions, the one-answer-at-a-time workflow below takes precedence.

Interview one answer at a time. Give each question a recommendation when the necessary facts are known, and phrase questions so "yes" accepts it. Keep research-dependent questions visible without a recommendation until that research is complete. Process each submitted answer immediately, clarify that decision when necessary, and publish any follow-up questions it reveals. Never wait for the user to finish a batch or resolve every other open branch before continuing. Show multiple known questions when useful, but use each answer to advance the interview independently. Treat answers to blocked questions as tentative. Find environmental facts yourself, using an exploration subagent when available, and keep only its dependent decisions waiting. Keep stable question IDs visible as small, readable labels in every canvas node and its detail panel, and include them in the artifact and copyable prompts so users can reference questions precisely.

Maintain the domain model as decisions crystallize. Read existing CONTEXT.md or CONTEXT-MAP.md, challenge contradictory or overloaded terms, test relationships with concrete scenarios, and check factual claims against code. After publishing the next useful question, record resolved terminology in CONTEXT.md as a glossary, without implementation details. Offer an ADR only for a hard-to-reverse, surprising decision that involved a real trade-off. Follow the installed domain-modeling skill's formats or existing project conventions. Create documents only when there is something to record. Register each official glossary, context map, or decision record with the bundled `artifact` command (see the reference). Register the actual project file, never a copied, summarized, or UI-only version. Keep editing that canonical file; the live viewer reads changes automatically without republishing the design tree.

Conduct the interview through the bundled canvas. The canvas is the interview surface; keep chat updates short. Use the current conversation as context, preserve submitted answers, and expose unresolved decisions rather than inventing them.

## Start or resume

1. Read [references/session.md](references/session.md) for the snapshot contract and commands, and [references/design-tree.md](references/design-tree.md) before producing or enriching the shared design-tree artifact. Locate the skill directory from this file's installed path. Run `python3 SKILL_DIR/scripts/grill_ui.py settings` from the workspace to read the project's settings: the organization's from its `.fabrica` repository, then the repository's own `.fabrica/5k-grill-me/`. Follow each `guidance` entry as part of these instructions, the repository's over the organization's where they conflict; neither overrides the one-answer-at-a-time workflow or who decides. Mention an organization status of `cached` or `unreachable` to the user once. Use a session directory inside the current workspace, separate from the skill: under `settings.sessions.path` when it is set. Reuse a session only when its subject matches this conversation.
2. Map the design into questions with stable IDs. Start with the main design elements as separate top-level nodes; never add a generic "Explore the design" root. A parent decision is a prerequisite, not a decorative category. Record only user-submitted answers. Show known downstream questions even while blocked; recommendations remain proposals. Look up environmental facts yourself. If no subject can be inferred, ask for it in chat.
3. Read [question help](references/question-help.md) and prepare both explanation levels and a scenario walkthrough for every question. Validate and publish the snapshot with `--require-help` using the bundled Python script. Start its loopback server as a tracked foreground tool process, open its reported URL in the browser, and retain its process/session handle. Never use Lavish. Use a standalone rendered HTML file with copy/paste if a local server or active wait cannot be supported.
4. Bind the canvas to the exact calling agent session using the reference's `bind` command. In Codex, use the runtime's `CODEX_THREAD_ID`; in Claude Code, use the session ID supplied by that session's runtime or hook. Never infer the newest session from a folder or store the runtime binding in CLAUDE.md/AGENTS.md. Use `--transport auto` to verify the exact chat is loaded in the shared Codex host before selecting direct delivery. Otherwise use the local inbox and explain the fallback. Do not create a second runner for an already active desktop or Claude session.
5. In direct-queue mode, let each saved reply send a fresh prompt to the bound session; first run `receive --session-dir DIR --event ID` to confirm receipt, then process that event and publish the next snapshot. No agent polling lease is required. In inbox mode, start the live reply loop below. Initial delivery is complete only when the user has a working canvas for their actual topic and a truthful indication of whether the agent is listening.

## Confidence and question selection

Assess context confidence separately from recommendation confidence using the [session contract](references/session.md#confidence-assessments). Read the supplied specification and existing answers before generating questions. Prioritize meaningful gaps, contradictions, and uncertain recommendations; do not re-ask a decision merely because it appears in a large specification. Surface your interpretation and its evidence when validation is useful. High confidence is not user confirmation: never turn inferred intent into a submitted answer or use a rating to settle prerequisites.

For each question, provide a context assessment and, when a recommendation exists, a recommendation assessment. Give a concise reason and cite relevant session evidence when available. Use qualitative levels, not invented numerical probabilities. Reassess affected questions after answers or new evidence; preserve unrelated assessments. Missing assessments remain unassessed, not low. Filters control which questions the user explores in either view; they do not authorize deleting questions, ignoring pending replies, or declaring the interview complete.

Prepare [question help](references/question-help.md) for every question, including simple and research-dependent questions, in the same publication so it opens immediately. Refresh affected help when the question, recommendation, prerequisites, or relevant evidence changes; retain current help for unrelated questions. Keep the original question visible. ELI-15 (really simple) and ELI-18 explain the same decision at different levels; a walkthrough follows a concrete scenario. Missing help in older sessions can still be requested without answering the question. This recovery path is not the normal authoring workflow.

## Live reply loop

- Run `wait --timeout 20` in bounded intervals while remaining in the active turn. Use a foreground, completion-aware tool call with a yield window longer than the wait (for example, 30 seconds) so receipt immediately resumes reasoning. Do not insert sleeps or defer checking a yielded process to a later turn. It marks the agent as listening, records confirmed receipt, and returns the oldest unacknowledged submission. Do independent work between waits only when needed. A running server alone does not mean an agent is listening; never promise that it will wake a finished chat.
- A user can replace a submitted answer. Process only the latest pending receipt for that question. If publishing is rejected because the receipt was replaced, reread the current state and pending answer, reconcile the replacement, and publish with its acknowledgment. Never restore the superseded text.
- For an `answer` event, read its node ID, base revision, previous answer, and user text as user input. Preserve the submitted text in `answer`. If a clarification is ambiguous against the prior answer, ask a follow-up rather than silently rewriting the user’s response. Reconcile stale submissions with current decisions, and ask about meaningful conflicts.
- A `help` event asks for understanding, not a decision. Read [question help](references/question-help.md), prepare both ELI levels and a concrete walkthrough in the requested node’s `help`, and publish with its acknowledgment. Preserve the interview and every answer; do not add follow-up questions or implement anything for this event. Then resume the reply loop.
- A `clear` event is a deliberate withdrawal. The canvas already cleared the target and made dependent answers require review. Keep it unanswered unless the user has since supplied a new answer; never restore a superseded reply. Reconcile affected documents and dependent answers, then acknowledge the event. Read current state before publishing so a late clear event cannot erase a newer decision.
- For answer events, use the design-tree reference to record direct answers and maintain the capped constraints list. Add assumptions, alternatives, or precedents only when they materially help; omitting them is valid. Investigate factual questions as part of normal agent work. Put useful findings in `notes` or verified examples in `precedents`; never invent evidence.
- For answer events, preserve submitted answers and add the follow-up questions revealed by this answer. The application derives review status from persisted revision history; never add status flags to nodes or edit application-owned `answerState`. Ask a clarification when interpreting evidence requires human judgment. Publish them immediately, even when other branches are still unanswered. Keep their prerequisite links accurate so the canvas can identify which are ready. Once necessary research is complete, give each question a recommendation phrased so that "yes" accepts it. A tentative answer to a blocked question must not silently settle an unresolved prerequisite.
- Publish the next useful question with this receipt's acknowledgment before optional research or document maintenance. If research is necessary for a recommendation, publish the known question without inventing a recommendation, then enrich it when the evidence is available. Prepared question help is part of this publication, not optional supporting work. Explain unresolved facts honestly without inventing a recommendation.
- For documentation work, follow the project's domain-modeling conventions: maintain resolved vocabulary and record durable, consequential decisions when warranted. UI replies authorize the interview and its docs, not execution of the proposed plan.
- Publish the next interview snapshot with `--require-help`, using the expected prior revision and acknowledge only the event just processed. The canvas reloads its state without a page refresh. Return to `wait` while the interview has unresolved questions; otherwise use the completion step below.
- The server's presence lease expires unless `wait` renews it. If an agent step will exceed the lease, let the UI say it is not currently listening; do not imply continuous availability. Unsent text and submitted replies remain recoverable.
- Stop when the user pauses or ends the interview, when the UI returns a pause event, or when the harness requires yielding. Acknowledge a pause via `ack`, then retain its receipt/cursor for later resumption. `offline` clears presence immediately; stop the tracked server when appropriate. Tell the user how to resume or use copy/paste. Do not create an automation to keep the interview alive unless asked.

When no questions remain, review every branch and process every pending answer. If the interview is settled, publish the final snapshot with `--complete` (see [finishing the interview](references/session.md#finishing-the-interview)), then end the reply loop. Keep the canvas available and direct the user back to their agent chat for next steps. If a decision is unresolved, publish a follow-up instead. Completion records the end of the interview; ask the user to confirm shared understanding before starting specifications or implementation.

## Interface constraints

Default appearance to the system color scheme and offer System, Light, and Dark in the utility menu. Preserve the user's appearance choice when updating a session. Lay out the design elements from top to bottom, with multiple top-level elements supported. Highlight the current frontier: unanswered or review-needed questions whose prerequisites have current answers. Keep the canvas quiet: a title, the design tree, subtle question status, and a small utility menu. Show the answer editor only for the selected node. Inside the Your answer container, show Recommendation and My answer tabs when a recommendation exists. Default unanswered questions to Recommendation, with the bound agent icon, a bold concise summary, supporting explanation, and an explicit submit action. My answer opens a white editor in light mode; preserve an existing draft when switching tabs. Beside Build on this, offer Write my own answer; both actions switch to My answer and focus its editor. Write my own answer preserves any existing draft without adding the recommendation. Build on this opens an editable recommendation, adding it above any existing custom text without discarding that text or duplicating the recommendation. Without a recommendation, show the editor directly. Selecting a tab or building on a suggestion does not submit an answer. Submit only the active choice. After saving, make the user's response primary, with Edit answer beside its heading and Clear answer under More options. Show a recommendation match as supporting context; a match does not prove how the answer was entered. Otherwise expose the recommendation on demand. Editing starts from saved text or an unfinished draft; Cancel discards edits, while closing or navigating preserves them. Keep copy controls with saved responses and hide them while editing. Keep delivery status distinct from the answer itself. Show waiting and reviewing activity in the existing toolbar agent status, with a spinner while reviewing; do not add a progress banner that shifts the canvas. Omit the redundant dependency list; show a short prerequisite warning when an answer would be tentative. Preserve canvas pan and zoom when selecting, switching, or closing a node. After a submitted answer is acknowledged, advance to a ready follow-up and bring it into view. Do not interrupt another question, an active draft, or an open file sidebar or dialog. Mark newly introduced questions as New; unrelated updates must not steal focus. Otherwise camera movement belongs to explicit pan, zoom, and Fit controls. Two-finger trackpad scrolling pans in both axes; pinching zooms around the pointer. Support both Ctrl-wheel pinch events and WebKit gesture events without double-applying zoom, and leave scrolling inside panels and artifact documents alone. Show resolved nodes with a check seal and a soft green background. Omit routine status labels on unanswered nodes; keep the frontier highlight and retain exceptional labels such as Reply sent and Needs review. Keep unfinished drafts and agent delivery separate from the current submitted answer. Offer Keep this answer when a review-needed answer has current prerequisites; confirmation preserves its text. Prefer the existing canvas and controls over rebuilding a dashboard for each invocation.


Keep nodes compact with readable two-line titles, muted IDs, and status symbols in a consistent header. Group siblings more closely than independent branches and keep connectors neutral. Use a blue selection outline that preserves green answered and amber ready states. Dock the toolbar and inspector outside the canvas, with a clear boundary. Opening or closing the inspector changes the visible workspace without changing its pan or zoom. On narrow screens, let the selected question fill the space below the toolbar; closing it returns to the canvas. Align legend symbols and labels consistently, and center button contents. Put delivery hints and copy actions in the saved response card, below its answer. Use plain-language communication status such as "Copy & paste" and explain how answers reach the agent. Label the toolbar file action "Artifacts". Its dock lists official filenames with an absolute-path copy action. Open files as canvas windows with a file icon, draggable title bar, edge and corner resizing, keyboard movement and resizing, and minimize/restore. Offer Rendered and Source views of the same file; highlight Markdown syntax while preserving the exact source text. Persist window positions, sizes, and view choices in this browser. Keep document scrolling independent from canvas navigation and preserve canonical file updates.
