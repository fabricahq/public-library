# 5K PR Review

A 5K PR review is the 5,000-foot view of a pull request: high enough to see the shape of the change, low enough to make out its tables, entities and decisions.

Help a reviewer understand a pull request: what it created, what it changed, how the pieces relate, and how it was verified. This is not a bug review. Never report defects as findings; adversarial code review covers that. Describe what is there, with literal examples, so the reviewer gets a feel for how it works.

The output is one self-contained page: a section rail, a pannable canvas, and an inspector that opens when a node is clicked. You write a JSON snapshot; the bundled script renders it.

## Gather

1. Read the PR: title, body, base and head branches, the stack it sits on, stats, commits, review comments and CI status. Read the repository's planning or decision records the PR touches; they are the best source for why.
2. Diff base against head. Work from the merge base (`git diff base...head`).
3. If you are the agent that built the PR, collect your own verification from this session. Otherwise take it from the PR body, commits and comments, and say so in `verification.agentNote`.
4. Read the settings. They can live in two places: the repository's own `.fabrica/5k-pr-review/settings.yaml`, and an organization's defaults in `5k-pr-review/settings.yaml` on the default branch of its `.fabrica` repository (`<owner>/.fabrica`, beside the organization's other Fabrica tools' folders), when that repository exists and you can read it. Each top-level key the repository's file sets replaces the organization's. Copy the personas into the snapshot's `personas`, so the page's Settings shows them. Use them to write descriptions in the product's own terms: name a persona when a change matters to particular people ("Field agents can now..."), and otherwise say "users". If the file is missing, say "users"; never invent personas. Copy its `catalog` block into the snapshot's `catalog` as well; it is off unless the file turns it on. Both files are optional: without them the skill runs with no personas and no catalog.

## Scan quickly

The scripts in `scripts/` do the mechanical half of a scan, so your own time goes to the writing. Each prints JSON; keep their outputs beside the snapshot's build, so a rescan can reuse them.

1. **Wait for the branch to settle.** Run `scan.py changes --repo . --base BASE --head HEAD`. While `headAgeMinutes` is under 10 or `commitsInLast15Minutes` is above zero, someone is still pushing: write the sections the moving files don't touch first, and scan those files last. Just before you publish, read the PR's head again; if it moved, rescan what changed.
2. **Rescan only what changed.** Record the commit you scanned in the snapshot's `scan.head`. On a rescan, run `scan.py changes ... --since <scan.head>`: its `redo` says which steps to repeat (`schema`, `backend`, `goDeadcode`, `frontend`, the files whose `props` to read again, `catalog`, `knip`, `install`, `evidence`, `stats`). Reuse everything else from the last build.
3. **Let the scripts do the mechanical steps.**
   - `scan.py checkout --dir DIR --ref REF` makes or moves a scratch worktree, and installs JavaScript dependencies only when the lockfile changed since that tree's last install.
   - `scan.py schema --format goose|plain --out DIR` applies the migrations at base and head, read from git, to fresh databases, and writes both dumps and a diff by table, column, constraint, index, policy and function. Set `PR_REVIEW_PSQL` and `PR_REVIEW_PG_DUMP` when `psql` needs another user.
   - `scan.py stats`, `scan.py components --frontend DIR` (components with their JSX edges and levels, bottom-up) and `scan.py deadcode --base-dir A --head-dir B` (knip, deadcode and staticcheck at both, diffed).
   - `node scripts/props.cjs FRONTEND '[[file, export], ...]'` reads each component's properties from the type of its first parameter.
   - `node scripts/catalog-code.cjs FRONTEND CATALOG_FILES...` takes each catalog state's code from its file.
   - `node scripts/walk.cjs BUILT_DIR STATES.json THUMBS_DIR [CONCURRENCY]` renders every state several pages at once, reports each one's errors, and screenshots each component's first state in both themes, clipped to what it draws. It serves the build through Playwright's routing, so no server listens.

## Sections

Write each section that has content. Leave a section out rather than inventing it.

- **database**: every table the PR creates or changes, plus the unchanged tables they reference, shown as context. Get the schema by running every migration on a fresh database at the base and at the head and diffing the dumps; never reconstruct columns from reading migrations alone. For each table say what one row is in a few words (`row`, such as "One task, assignable to a person."), what the PR changes as short bullets (`explain`, a list), each column's status (`new`, `changed`, `renamed` with `from`, `removed`, `same`), listing every column of every table shown, context tables and unchanged columns too, one entry per column, so the board and the chat show what a row holds, the column it references (`ref`), the values a check constraint allows (`values`, with the constraint's name in `valuesRule`), its constraints and access policies in plain words, and the migrations that touch it. Write example rows with realistic values that show each new column doing its job, load them into the head database, and keep only rows it accepts. Try at least one row each new constraint should refuse and confirm it does. When a migration rewrites existing data, insert a row at the base, run the PR's migrations over it, and show it before and after in `dataMigration`, naming the table it belongs to in `table`.
- **backend**: new and changed types, enums, views, rules, store interfaces and API operations, grouped by what they are for. Give every property of a changed type, unchanged ones marked `same`, with its status (`renamed` with `from`), a one-line meaning and any fixed set of `values`, and a JSON example that matches the database example where they overlap.
- **frontend**: new and changed components, bottom-up so a reviewer meets the parts before what is built from them: building blocks that draw no other component of the PR first, then components made of them, and the whole screen or panel last. Find the edges by JSX use, not imports, since an import of a type or helper draws nothing. Give each component `madeOf` (the PR's components it draws) and `usedIn` (those that draw it). Then a last group, `Logic: hooks and utils`, for code with no screen of its own (kind `hook` or `util`). Say where each shows, what it takes, and a short example. Read each component's properties from its source at the base and the head, the type of its first parameter, never from memory or an earlier scan, and list every one: all of a new component's properties are `new`, a changed component's compare by name and declared type (`changed` says what it was), and a property the head dropped is `removed`. The same holds for the properties of a new backend type. Mark hand-drawn text examples `"lang": "text"`, which the page labels as a sketch. Leave out generated types and schemas that mirror the backend; count their files and lines in the summary.
  - **Previews.** Give each component a `preview` so its card shows a screenshot and its window shows the real component, live, in every state worth seeing, with the code each state runs beneath it. The preview is `{"url", "component", "states": [{"id", "title", "code", "codeFrom", "status"}], "thumb", "thumbDark", "size": [w, h]}`: the canvas draws a tab per state, frames `<url>?c=<component>&s=<id>&shot=1&theme=light|dark`, and shows the state's `code` under it, highlighted. `status` is `new` or `changed` for a state the PR adds or changes; `size` is the screenshot's CSS pixels, so the card keeps its height before the image loads. Check every state renders without errors and screenshot the first state of each component in both themes. Publish what the frames load and the screenshots under `previews/` beside the canvas; on a rebuild, publish every file the build's `index.html` names and remove the ones it no longer names, since a style change renames the stylesheet too and a preview missing it renders unstyled. Where the previews come from depends on the settings, and works without them:
    - **The project's catalog**, when `catalog.enabled` is true. Read `catalog.about` to learn how the catalog is laid out and how its URLs name a state. Find each changed component's states at the base and the head, from the catalog's index or its files: a state missing at the base is `new`, and one whose catalog file changed is `changed`. Build the catalog from the head in a scratch copy, with an entry that starts it from any folder, and publish it under `previews/catalog/`, so it shows for every viewer and at the scanned commit; set `"source": "catalog"`, and set `live` to the component's page in the deployed catalog (`catalog.url` with `{pr}` and `{sha}` filled in), which the window links. Take each state's `code` from its catalog file: what the state renders, the file's own helpers it calls, the imports those use, and its controls' starting values; set `codeFrom` to the file. When a changed component has no states in the catalog, build none of your own: set `preview` to `{"source": "catalog", "missing": "..."}`, saying in one sentence which catalog file to add beside which component, under what contract, and the command that regenerates the index; the card says it has no catalog states yet and the Preview tab shows that sentence.
    - **A page of your own**, the default when there are no settings or no catalog. Build it from the PR's own frontend in a scratch copy: an entry that renders one component per `?c=<component>&s=<state id>`, bare with `&shot=1`, in `&theme=light|dark`, answering its API calls from an in-memory fake that holds sample data and applies changes, so the component can be used, not only looked at. Give any bar the page keeps in view, such as its state tabs, an opaque fill, so content scrolling under it doesn't show through; check that by scrolling a tall state. Write each state's `code` as an app would: the imports it needs, the lines that get its data (a hook call or `useState` with the state's value), and the element with that state's props, one prop per line when long, in the app's own names, never the harness's helpers or fixture constants. Never commit it to the repository under review.
- **architecture**: decisions that change how the system is shaped. Each has before, after, why, trade-off and its source, and a small `diagram` of the before and the after: rows of boxes, `→ label` arrows and stacks, with boxes toned `new`, `changed`, `removed` or `muted` (see the example). Rate each decision's `significance`, which the board groups by: `foundational` when it is hard to reverse and later work builds on it (data model, integrity, contracts other contexts rely on), `significant` when it shapes how one feature works or what it promises, and `local` when it is a detail inside one area that is cheap to change. List decisions most significant first within each level.
- **principles**: rate the PR against each principle in [references/principles.md](references/principles.md) as `strong`, `mixed` or `weak`, with a one-line verdict and concrete evidence from this PR. List each red flag with whether you saw it and where. For each one you saw, draw the `issue` the same way as a decision's diagram and propose a simple `fix`, with its text and diagram. Rate design, not correctness. Each principle and red flag window carries a handoff prompt the reader can copy to an agent working in the repository; the page builds it from the PR, the rating and the evidence. For each principle rated `mixed` or `weak`, add a `handoff`: one to three sentences naming the specific change that agent should make, with the files or records it touches. A red flag's prompt uses its `fix`, or its own `handoff` when it has one.
- **verification**: runs of any `verify-*` skill (what was walked, what it found, what was fixed), the checks that ran and their results, what was found and then fixed during the work with commit references, and what was not verified. Add what you did to check the canvas itself.
  - **verification.evidence** (experimental): don't take the PR's word for what it verified. List what the change should prove, each from something in it: a rule the schema adds, a recorded decision, a fixed bug, or something a person sees. Then find evidence the PR can't self-report: tests the diff adds or changes, found by name and file; the CI step that ran them, checked to have passed at the head and unable to skip them; showcases or recordings a deploy made; and checks you ran yourself. The PR's own description counts only as a claim. Mark each expectation `proven`, `partial`, `claimed` or `missing`, say the gap for anything short of proven, and give a `handoff` naming the test that would close it. Shape: `{"experimental": true, "method", "limits", "sources": {key: {label, url, result}}, "expectations": [{id, title, from, status, evidence: [{kind: test|e2e|showcase|ci|schema|claim, name, file, detail, ran: sourceKey}], gap, note, handoff}]}`. In `limits`, say what you couldn't see, such as a CI log you couldn't read.
- **deadCode**: what the PR left unused. Run the language's dead code tools on the base and the head and diff the findings, so the PR's own leftovers stand apart from what was already unused. For Go, run `deadcode` with and without `-test` from every main package, including build-tagged ones, and `staticcheck -checks U1000`; for TypeScript, run `knip` from the app entry, routes, scripts and tests, writing a config in a scratch copy when the repository has none. Group findings as `Left by this PR` and `Already unused before this PR`, with at most five in a group; put related names in one finding with `entries`. Each finding has `name` (or a plain `label` when it covers several names), `where`, `status` (`new` or `existing`), `finding`, `why`, `fix` and `tool`. Check each one by hand before listing it. Code reached by reflection or bindings is not dead, so leave it out. An export only its own file uses is an unneeded export rather than dead code, and a type that names part of an exported signature is usually fine to keep; say which in `finding` and `fix`. Count findings in generated files in the summary instead of listing them. List each tool in `scans` with its scope, counts at base and head, the command, and what it can miss.
- **media**: screenshots and recordings from the PR, its preview build or its showcase runs. Embed images you can read as `data:` URIs in `src`; link the rest. The canvas works without media.
- **overview**: a headline and what users can now do. Group it by the system's own things, such as Tasks or Workflows, then by subgroups within each (`group`, `icon`, `subgroups` of `group` and `items`). Name each subgroup for what people can now do, as a short verb phrase such as "Track status" or "View and assign teammates' work", never a bare noun.

## Render and deliver

1. Write the snapshot to match [examples/invoice-installments.json](examples/invoice-installments.json), a made-up PR that uses every field. Keep example ids and names consistent across sections, and list them in `people` so the page can name the person beside each id.
2. Render it: `python3 scripts/render.py SNAPSHOT.json OUT.html`.
3. Open the page in a browser once and check that the schema view reads well, then give the reader the page. The page pushes apart tables that would overlap, and the reader can drag a table by its header; the layout is kept in their browser until Reset layout.
4. When you publish it as a claude.ai Artifact, declare `capabilities: {"sample": {}, "comments": {}}`. The reader can then chat about the PR from the toolbar, or highlight any text and ask about it: Claude answers in a bubble from the snapshot alone, so the page never waits on you. Each answer names the parts of the snapshot it used, as links to their windows, and "See Claude's context" lets the reader browse and search the snapshot itself, so its limits are visible. A question that needs the code goes to you as a comment on the highlighted text; you are woken by it, answer from the repository in that comment thread, and never poll for questions. The toolbar's Rescan button sends you a comment on the PR title asking for a rescan: fetch the PR's latest head, rebuild the snapshot at it, redoing only what changed since `scan.head` (see [Scan quickly](#scan-quickly)), render and republish to the same page, and reply in that thread with what changed. Republish even when the head hasn't moved: the button spins until the page loads a version rendered after the request. Opened as a plain file, the page works without asking, and the Rescan button stays hidden.

Write for someone who has not read the code: plain sentences, the product's own words, no em dashes. Prefer short bullets under a plain heading to a paragraph.

Never show a list of more than five items flat. Group it under short headings, with at most five items in a group: in the overview by the system's own things (see **overview**), and for verification runs by a `group` on each run.

Put field, column, type and operation names in backticks, such as `description` or `tasks.create`; the page shows them as code.
